## 1. The motion chain was wired wrong

**`collision_monitor.cmd_vel_out_topic` was `cmd_vel_nav`.** But `nav2_bringup`'s
`navigation_launch.py` remaps `cmd_vel` → `cmd_vel_nav` for controller_server,
behavior_server **and velocity_smoother** — so `cmd_vel_nav` is the smoother's *input*.
Two consequences:

1. **Feedback loop**: monitor → smoother → monitor, made worse by `feedback: OPEN_LOOP`
   (the smoother ramps from its own recycled output).
2. **Collision-monitor bypass**: anything reading `cmd_vel_nav` also received
   controller_server's **raw, un-smoothed, un-gated** command at 20 Hz, interleaved with
   the gated one. The SafeZone/SlowZone stops never actually held the robot.

Correct chain (now):
```
controller_server → cmd_vel_nav → velocity_smoother → cmd_vel_smoothed
  → collision_monitor → cmd_vel_shim → safety_guard → /cmd_vel → ESP32
```

**`cmd_vel_deadband.py` retired.** Built for the old open-loop L298N firmware, it
re-floored every command to `vx>=0.20 / wz>=0.80`. A fine MPPI correction of
`(0.02, 0.05)` reached the wheels as `(0.21, 0.80)` — a hard swerve. That is the weave.
Firmware v2 does closed-loop PID on real m/s with `gMinDuty` for breakaway.

**`run_stack.sh nav2` stacked duplicate nav2 instances** (no kill-guard, unlike
`fuse`/`remap`) → duplicate action servers → `unknown goal response, ignoring...`,
`BtActionNode::Tick: invalid status value`, random aborts. Guard added.

## 2. The floor was mapped as an obstacle

Deprojecting the depth centre column: **open floor lands at z = +0.04 m**, while
`esdf_slice_min_height` was **0.05** — 1 cm of margin, well inside depth noise (which is
extra-sparse because the IR emitter is off for cuVSLAM scale).

Result: a solid inflation plateau across the full ±1 m width starting ~0.25 m ahead,
**with no lethal cells anywhere**. MPPI crawled at 0.082 m/s (`vx_max` is 0.30), the
SlowZone cut that to 0.033, the rover covered **0.9 cm in 30 s**, and nav2 aborted on
*"Failed to make progress"*.

Now `0.12` (slice height 0.20), and the same trap fixed in `collision_monitor.min_height`.

> The +0.04 also implies the `base_link → camera0_link` static TF in `run_stack.sh`
> **overstates camera height by ~4 cm** (publishes z 0.20; data implies ~0.16).
> **Worth a tape measure** — fixing it lets the band come back down.

## 3. The costmap thought the robot was half its real width

Footprint was `±0.085` = **17 cm wide**. `HARDWARE.md` and the firmware both put the
wheel track at **34 cm**. It planned through gaps the rover cannot fit. Now `±0.19`.

## 4. nav2's collision monitor had no usable obstacle source

Its source was nvblox `back_projected_depth` — an nvblox **debug visualisation** topic,
measured at **0.47 Hz with gaps up to 7.3 s**. When a source goes stale the monitor
fail-safes to *"Robot to stop due to invalid source"* and **holds the robot at zero**.
So nav2 was pinning the rover while planning normally.

(`publish_debug_vis_rate_hz: 10.0` was tried — **no effect**, that param does not gate
this topic. Reverted rather than left as a misleading no-op.)

Fix: **`nodes/depth_to_cloud.py`** — strided depth → PointCloud2 at **10 Hz**.

## 5. Goals were rejected before the robot ever moved

`GridBased plugin failed to plan: "Unable to transform poses to global frame"`.
Goals are in `map`, costmaps in `odom`, and `/tf` has gaps up to 0.37 s — so a goal
stamped `now()` is repeatedly in TF's future. Fixed with **goal stamp = 0** ("latest
available") plus `planner_server.transform_tolerance: 0.6`.

## 6. The target coordinate swung whenever the robot turned

`detections_3d` looked up TF **after** YOLO inference, so the transform lagged the image
by 100–250 ms. At 0.9 rad/s that throws a 2 m object **~0.4 m sideways** — so the goal
moved every time the rover turned, and the approach chased a ghost.

Fixed by snapshotting TF **before** inference, plus a per-label EMA.
Measured after: **x sd 0.9 cm, y sd 0.1 cm** on a stationary bottle.

## 7. Perception lost the bottle exactly as it got close

Two separate failures, both measured on the real bottle:

- **Label flips with range** — same object, same box: `bottle 0.70` at 2.3 m, but
  `vase 0.40 / bottle 0.15` at 1.4 m. yolov8n is 3.2M params; this is inherent.
  → confidence gate 0.45 → **0.35**, plus an `ALIASES` table ({bottle, vase} etc.).
- **Translucent objects on polished marble return no centre depth**, so a perfectly good
  2D detection was silently dropped.
  → fallback samples the whole box and takes the **20th percentile** (nearest surface;
  median would bias onto the wall behind).

Also: `approach_object.py` rewritten from 8 stop-go steps (which forced an in-place
rotation at every step) to **one continuously-updated goal**, and **losing sight no
longer aborts** — the object is grounded in `map` and the robot is localized, so it
drives to the last known coordinate.

## The big one: cuVSLAM fails silently

**I initially mis-diagnosed this as "cuVSLAM under-reports translation ~8x on polished
marble". That was WRONG.** The real chain:

1. Orin saturates (6 cores, load ~9, ~500 MB RAM free).
2. D555's DDS reader callbacks fall behind — `callback took too long!` in
   `/tmp/realsense.log`.
3. **Stereo IR collapses 22 Hz → 0.97 Hz** (depth 21 → 1.2 Hz).
4. cuVSLAM **freezes**: process alive, `slam=True`, frame counter still rising — but
   `base@odom` stops changing and it **stops publishing `/odom`**. It does **not**
   recover when images return; it must be restarted.
5. The EKF coasts on gyro alone → yaw drifted **~40° while parked with motors dead** →
   every behaviour keeps navigating on that fiction.

**Proof it is load, not texture:** killing `detections_3d` + `pixel_to_goal` +
`depth_to_cloud` restored IR **0.97 → 27.2 Hz instantly**.

### What now guards against it

**`nodes/odom_health.py`** publishes `/odom/health`, cross-checking three independent
stories about distance travelled — commanded (`/cmd_vel`), visual (cuVSLAM `/odom`),
and wheels (`/wheel_odom`) — plus IR liveness:

| status | meaning |
|---|---|
| `VO_STALLED` | no `/odom` for >1.5 s — cuVSLAM frozen, **restart it** |
| `CAMERA_STARVED` | stereo IR <10 Hz — Orin saturated, cuVSLAM about to freeze |
| `VO_UNDER_REPORTING` | commanded a real drive, visual barely moved |
| `VO_DRIFT_STATIONARY` | told to hold still, pose wandering |
| `VO_SCALE_OFF` | encoders and camera disagree about distance |

`trust: false` ⇒ do not start a move, do not believe any "arrived".

- **`odom_move.py home` REFUSES** on an untrusted pose (`--force` overrides).
- **`approach_object.py`** reports arrival as **UNVERIFIED** (exit code 2) instead of
  faking success.

**CPU is a safety property here.** `imu_to_base.py` was burning **37% of a core** doing
four numpy allocations per sample at 199 Hz — rewritten to a precomputed 3×3 matrix with
plain floats plus a 100 Hz cap (**verified bit-identical**, worst diff 6.7e-16).

## Current blocked state

**1. D555 ethernet link is down.**
```
enP8p1s0: <NO-CARRIER,BROADCAST,MULTICAST,UP>   carrier: 0
```
Interface is enabled and healthy; there is simply no electrical link. **Check the PoE
injector's power LED first** — this is cable/power side, not software. (Distinct from the
dead-DDS-server case, where the camera still *pings* but reports "No RealSense devices".)

**2. ESP32 still on old firmware.** `/wheel_state` is exactly **1.000 Hz** — the old
`EXECUTE_EVERY_N_MS(1000)` path. HEAD has published at 50 ms (20 Hz) since `f4be55a`
(2026-08-08), so **the source needs no change**. Two things went wrong instead:

- **Wrong flash target.** `rover-esp32.local` → **192.168.1.12**; the docs said
  `192.168.1.11`, where a *different device* answers. Fixed in `2918450`. Pick
  `rover-esp32` from the Arduino IDE's network port list — do not type an IP.
- **Truncated file.** The local working copy had lost its final `}` (28 `{` vs 27 `}`)
  and **could not compile**. Restored from git. **Use `git pull`, not copy-paste.**
